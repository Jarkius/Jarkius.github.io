แชทไม่ใช่ที่เก็บความจริง: ทำไม AI agent ของคุณถึงลืม (และวิธีแก้ด้วยไฟล์ธรรมดา)

1 กันยายน 2026 · dev notes

ผมเคยเชื่อว่าเอาทุกอย่างยัดใส่ AI ครั้งเดียวแล้วมันจะทำได้หมด — เจ็บมาก่อนถึงเลิกเชื่อ

โพสต์นี้เขียนไว้เตือนความจำตัวเองเป็นหลัก ไม่มีอะไรจะขาย ใครเคยผ่านเคสแบบนี้คงแอบยิ้มมุมปาก 😆

What — ปัญหาคืออะไร

สมัยก่อนผมสั่งงาน AI agent แบบนี้: เปิดแชทขึ้นมา แล้วเทกองทุกอย่างลงไปในครั้งเดียว — บริบทโปรเจกต์ สเปก ข้อห้าม ของที่ชอบ ของที่เกลียด ยัดยาวเป็นพืด กะเอาให้ครบทุกอณู แล้วหวังในใจว่ามันอ่านจบแล้วจะทำได้ครบทุกจุด เพราะพิมพ์ให้ครบแล้วนี่หว่า คงจะไม่พลาดหรอก

ผลคือไม่เคยเป็นแบบนั้น ช่วงแรกมันตอบดี แต่พอคุยไปเรื่อยๆ งานเริ่มแปลก มันทำของที่สั่งห้ามไปแล้ว แก้ไฟล์ที่บอกไปแล้วว่าห้ามแตะ บางทีก็ย้อนกลับไปใช้แนวทางเก่าที่เพิ่งตกลงกันว่าไม่เอาแล้ว — แบบไม่รู้ตัวเลย

ตอนนั้นผมโทษโมเดล เปลี่ยนโมเดล เปลี่ยน tool เขียน prompt ใหม่ให้สวยขึ้น ไม่มีอะไรแก้จริงสักอย่าง เพราะตัวปัญหาไม่ใช่โมเดล — ปัญหาคือผมเก็บความจริงทั้งโปรเจกต์ไว้ในกล่องแชท ซึ่งไม่ใช่ที่เก็บของแต่แรก

Why — ทำไมมันพัง

context window มีขอบ (ไม่ว่าโมเดลจะรองรับกี่ 100k–1M ก็ตาม) พอคุยยาวขึ้นเรื่อยๆ ของเก่าก็เริ่มไหลออกนอกหน้าต่าง และตัวที่หายไปก่อนคือข้อตกลงแรกของงานเสมอ — scope, อะไรทำได้, อะไรห้ามทำ, เป้าหมายจริงคืออะไร

ที่เจ็บที่สุดคือตรงนี้: ตอนที่มันจำไม่ได้ มันไม่หยุดมาถาม มันเดา แล้วตอบด้วยความมั่นใจเต็มร้อย เราก็เชื่อ เพราะมันพูดเหมือนมันรู้เลย

จุดเปลี่ยนคือวันที่ถามตัวเองว่า ถ้าแชทไม่ใช่ที่เก็บของ แล้วอะไรคือที่เก็บของ — คำตอบธรรมดามาก คือไฟล์ในโปรเจกต์ ไฟล์ไม่ลืม ไม่มี context window อ่านซ้ำได้ไม่จำกัด และอยู่กับ repo ตลอดไป ไม่ว่าจะเปิดรอบใหม่ เปลี่ยนโมเดล เปลี่ยน agent หรือส่งต่อให้คนอื่นทำต่อ

แชทคือที่สั่งงาน ไฟล์คือความจริงและกติกากลาง ความจริงห้ามอาศัยอยู่ในแชทเด็ดขาด

How — โครงที่ใช้จริง

โครงนี้ไม่ได้ออกแบบเสร็จในหัวรอบเดียว มันคือผลของการงัดแงะ เจอปัญหา ลองผิดหลายสิบรอบ ใครอ่านแล้วรู้สึกว่าตัวเองไม่เก่งพอจะทำแบบนี้ ผมยืนยันได้เลยว่าไม่เก่งครับ แค่ถามเยอะและลองเยอะพอสมควร

ไฟล์ที่ติดมากับทุกโปรเจกต์ตอนนี้ (ไม่ต้องทำครบตั้งแต่วันแรก):

  • PROJECT.md — บอกว่ากำลังทำอะไร และอะไรไม่ใช่งานนี้ (scope, in/out)
  • AGENTS.md — บอกว่า agent ทำอะไรได้ / ห้ามทำอะไร (hard constraints, ไม่ต่อรอง)
  • SOT.md (Source of Truth) — บอกว่าความจริงล่าสุดของโปรเจกต์คืออะไร ตอนนี้ ไม่ใช่แผน
  • ROADMAP.md — บอกว่ากำลังอยู่ตรงไหน และจะไปไหนต่อ (แผนใหญ่ ไม่ใช่สถานะปัจจุบัน)
  • UX.md — บอกว่าผลลัพธ์หรือหน้าตาควรเป็นแบบไหน (ถ้างานมีหน้าตาให้ต้องดูถูก)
  • graft/ หรือ architecture doc — แผนที่ว่าโค้ดอยู่ตรงไหน เชื่อมอะไรกับอะไร

ทั้งหมดทำงานร่วมกัน — ขาดตัวไหนไป agent ต้องเดาในช่องนั้น และที่ที่มันเดา คือที่ที่งานเริ่มหลุด

เจอมาหมดแล้ว: ไม่มี PROJECT → งานคลาด scope. ไม่มี AGENTS → มันแตะของที่ห้ามแตะ. ไม่มี SOT → ทำซ้ำของเก่า. ไม่มี ROADMAP → ลำดับงานพัง. ไม่มี UX → ของที่ได้มาไม่ใช่ที่ในหัว. ไม่มี architecture map → แก้โค้ดผิดไฟล์

วงจรที่วิ่งอยู่ทุกวัน

  1. สั่งในแชทสั้นๆ เช่น "ทำ phase ถัดไปตาม ROADMAP" ไม่ต้องเล่าบริบทแล้ว เพราะบริบทอยู่ในไฟล์
  2. agent ไปอ่านไฟล์เหล่านี้เองก่อนเริ่มทุกงาน
  3. ลงมือทำตาม scope ที่ล็อกไว้
  4. จบงาน อัปเดต SOT.md + ROADMAP.md ก่อนปิด ทุกครั้ง
  5. ข้อตกลงใหม่ที่คุยกันในแชท ย้ายลงไฟล์ทันที ไม่ปล่อยให้ลอยอยู่ในแชท
  6. จบรอบ แชทหมดหน้าที่ เปิดใหม่ก็เริ่มจากไฟล์ ไม่ต้องเล่าอะไรอีก

รายละเอียดที่มักถูกมองข้าม — SOT.md ต้องมี timestamp

ไฟล์ที่บอก "สถานะปัจจุบัน" โดยไม่มีวันที่ประทับไว้ คือไฟล์ที่ไว้ใจไม่ได้ตั้งแต่บรรทัดแรก เพราะไม่มีทางรู้ว่ามันเก่าไปหรือยัง สิ่งที่ควรมีคือ:

  • Last updated — วันที่ล่าสุดที่แก้ไขไฟล์นี้
  • Last verified — วันที่ล่าสุดที่รันจริง (test, type-check ฯลฯ) แล้วยืนยันว่าสถานะที่บันทึกไว้ยังจริงอยู่

สองอันนี้ไม่เหมือนกัน — "อัปเดตไฟล์" ไม่เท่ากับ "ยืนยันแล้ว" การเขียนว่า "step X เสร็จแล้ว" ในไฟล์ ไม่ได้แปลว่ามันเสร็จจริง ถ้าไม่มีใครรันอะไรยืนยัน

อีกส่วนที่ช่วยมากคือ decisions log แบบ append-only ในตัว SOT.md — บันทึกเฉพาะการตัดสินใจที่ reverse ยาก, surprising ถ้าไม่มีบริบท, หรือมี trade-off จริง (แนวคิดคล้าย ADR แต่เบากว่า) ไม่ใช่ทุกการตัดสินใจเล็กๆ ถูกจดหมด — งานประจำวันไม่ต้องมี ไม่งั้นไฟล์จะบวมจนไม่มีใครอ่าน

Pro / Con

ข้อดี

  • แชทสั้นลงมาก งานส่วนใหญ่สั่งจบใน 2–3 ประโยค
  • เปลี่ยนโมเดล เปลี่ยน agent เปลี่ยนเครื่อง ทำงานต่อได้เหมือนเดิม เพราะความจริงอยู่ใน repo ไม่ได้อยู่ในกล่องแชทของใคร
  • โมเดลจำแม่นขึ้นเอง — ไม่ใช่เพราะโมเดลฉลาดขึ้น แต่เพราะสิ่งที่มันต้องจำในแชทน้อยลง
  • ส่งต่องานให้คนอื่น (หรือ agent ตัวอื่น) ทำต่อได้ทันที ไม่ต้องเล่าซ้ำ

ข้อเสีย / สิ่งที่ต้องระวัง

  • มี overhead — ต้องคอยอัปเดตไฟล์จริงๆ ถ้าไม่อัปเดต ไฟล์จะโกหกและแย่กว่าไม่มีไฟล์เลย เพราะดูน่าเชื่อถือแต่ผิด
  • ไฟล์หลายไฟล์เสี่ยงขัดแย้งกันเอง ถ้าไม่มีตัวไหนถูกกำหนดให้ "ชนะ" ชัดเจน (นี่คือเหตุผลที่ SOT.md ต้องมีสถานะที่สุดจริงๆ)
  • ไม่ใช่ทุกโปรเจกต์ต้องมีครบ 6 ไฟล์ — โปรเจกต์เล็กๆ อาจมีแค่ 2–3 ไฟล์ก็พอ การยัดไฟล์เยอะเกินจำเป็นก็คือการ "เทกองลงแชท" แบบเดียวกัน แค่ย้ายที่เทกอง
  • ต้องมีคนคอยตัดสินว่าอะไรควรอยู่ในไฟล์ (ความจริงที่คงอยู่) กับอะไรควรอยู่ในแชท (task เฉพาะรอบนี้) — เส้นแบ่งนี้ต้องฝึก ไม่ใช่มีสูตรตายตัว

เคสที่เจ็บจริง (จำได้นั่งซึมไปทั้งวัน)

แก้ไฟล์ผิดที่ — ให้ agent ปรับฟีเจอร์หนึ่ง คุยกันยาวเกินชั่วโมง งานออกมาดีทุกอย่าง พอเช็คเจอว่ามันแตะไฟล์ config อีกไฟล์ที่ตอนต้นแชทสั่งห้ามไว้เอง มันไม่ได้ดื้อ — มันลืม เพราะข้อความตอนต้นถูกไล่ออกจาก context ไปแล้ว ตอนนั้นโมโหตัวเองมาก เพราะรู้ว่าเป็นความผิดของวิธีสั่ง ไม่ใช่ของมัน ตอนนี้ข้อห้ามพวกนี้อยู่ใน AGENTS.md ซึ่ง agent อ่านทุกรอบ ไม่มีทางลืม เพราะไม่ได้พึ่งความจำเลย

เปิดรอบใหม่แล้วเล่าไม่ครบ — งานยาวทำจบในแชทเดียวไม่ไหว เปิดแชทใหม่แล้วนั่งเล่าบริบททั้งหมด เล่าไปก็รู้สึกว่ามันไม่ครบ แต่ไม่รู้ว่าตกอะไร สุดท้าย agent ทำผิดตามที่เล่าผิด ตอนนี้เปิดรอบใหม่บอกแค่ "อ่าน SOT.md แล้วทำ phase ถัดไปตาม ROADMAP.md" มันเดินถูกกว่าที่เล่าเองอีก

สร้างของซ้ำกับของที่เสร็จแล้ว — รอบหนึ่ง agent ทำฟีเจอร์เสร็จสวยงาม รอบถัดไปสั่งงานในแชทใหม่ มันสร้างฟีเจอร์เดิมขึ้นมาใหม่หมด เพราะในแชทใหม่มันไม่รู้ว่าของมีอยู่แล้ว วันที่เห็น diff ก็เซ็งสุดๆ เพราะงานตัวเองโดนทับตอนที่ยังไม่มีใครผิดเลย ตั้งแต่ใช้ SOT.md จดว่าอะไรเสร็จแล้ว ปัญหานี้หายไป

Future improvement

  • Memory ระดับ session/agent — ไฟล์ในโปรเจกต์แก้ปัญหา "ความจริงของโปรเจกต์" ได้ แต่ยังไม่ครอบคลุม "นิสัยการทำงานร่วมกันของฉันกับ agent" (เช่น ชอบ/ไม่ชอบแบบไหน, feedback ที่เคยให้ไปแล้ว) — ส่วนนี้กำลังทดลองทำเป็น memory อีกชั้นแยกจากไฟล์โปรเจกต์
  • Automated staleness check — อยากมี hook หรือ script ที่เตือนเมื่อ Last verified ใน SOT.md เก่าเกินไปเทียบกับ commit ล่าสุด แทนต้องจำเองว่าต้องไปเช็ค
  • Template ที่ generalize ได้ — ตอนนี้แต่ละโปรเจกต์ยังปรับมือทุกครั้ง อยากมี starter template ที่มีไฟล์พวกนี้พร้อมโครงว่างให้ copy แล้วกรอก ไม่ต้องเริ่มจากศูนย์

ถ้าใครอยากลอง

ไม่ต้องทำครบ 6 ไฟล์หรอก ผมเองก็ไม่ได้เริ่มครบ วันแรกๆ มีแค่ PROJECT.md — งานไหนต้องมาลงทะเบียนขึ้นชื่อโปรเจกต์ก่อน

แล้วถ้าวันหนึ่งนั่งคุยแล้วรู้สึกว่า agent เริ่มตอบแปลกๆ ทำของแปลกๆ อย่าเพิ่งโทษโมเดลเลย ลองดูก่อนว่ากำลังเก็บความจริงไว้ที่ไหน มันหาเจอไหม ผมโทษโมเดลอยู่นานมากกว่าจะรู้ตัว
